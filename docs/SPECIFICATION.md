# AgentSync：完整产品设计与 AI 开发执行总计划

Work 执行版

项目规划 v1.0 · 2026 年 10 月 19 日

这份计划整合了我们前面讨论的全部需求，包括七大协作问题、MCP 桌面端接入、API/SDK 接入、控制适配器、自主调度、免费开源以及 GitHub 发布。

我建议把 AgentSync 开发成一个独立于任何 AI 模型和客户端的多 Agent 协作与调度引擎。

它的最终目标是：

> 让 Codex、Claude Code、Cursor 等不同 AI Agent 能够共享上下文、自动分工、协调文件修改、交接任务、验证成果、管理权限，并在支持的情况下由 AgentSync 主动启动和调度。

### 两种运行模式必须同时规划

模式 A

MCP 协作模式

已有 Agent 主动调用 AgentSync，查询任务、同步进度与交换结果。

优先完成

模式 B

自主调度模式

AgentSync 通过厂商开放的 SDK/CLI，主动创建 Agent 会话并管理执行。

后续实现

共用同一个 AgentSync Core

统一任务数据库、权限、上下文和审计系统

这里有一个必须写入开发规范的边界：通过 MCP 接入客户端，不等于获得对该客户端的完整控制权。 控制适配器也只能使用厂商公开支持的能力，不能假定能够控制用户已经打开的任意桌面会话。

目前官方 MCP Python SDK 已支持 stdio 和 Streamable HTTP；Codex 提供 Python SDK，Claude 提供 Agent SDK，Cursor 提供 CLI 自动化接口。这些可以作为技术基础，但仍需要实际兼容性测试。

| 编号    | 工作内容                    | 验收标准              |

| M1-01 | Agent 注册、会话、心跳与在线状态     | 可区分不同 Agent 实例    |

SQLite 的 WAL 模式允许读写更好地并发，但同一时间仍只有一个写入者，并且不适合把 WAL 数据库直接放在网络文件系统上共享。

### M6 — 控制适配器（5 项）

这是此前讨论中特别重要的一环。

| 编号    | 工作内容                      | 验收标准                     |
| ----- | ------------------------- | ------------------------ |
| M6-01 | 统一 `AgentAdapter` 接口与能力声明 | 所有适配器使用一致的生命周期接口         |
| M6-02 | MockAdapter，模拟多个 Agent    | 无真实 API 也能测试调度           |
| M6-03 | CodexAdapter              | 可启动受支持的 Codex 会话并收集结果    |
| M6-04 | ClaudeCodeAdapter         | 可启动受支持的 Claude 会话并收集结果   |
| M6-05 | CursorAdapter + 运行管理器     | 能在支持的环境调用 CLI，记录失败、退出和超时 |

建议采用这样的能力接口：

```
class AgentAdapter:    async def capabilities(self): ...    async def start_task(self, task): ...    async def get_status(self, run_id): ...    async def get_result(self, run_id): ...    async def cancel_task(self, run_id): ...    async def resume_task(self, run_id): ...
```

这里仅是设计接口。某个客户端如果不支持取消、恢复或用量读取，必须明确返回 `unsupported`。

Work 需要分别核实并实现：

| 适配器         | 首选公开接口              | 注意事项                |
| ----------- | ------------------- | ------------------- |
| Codex       | Python SDK / 官方 CLI | 复用授权方式需实际确认         |
| Claude Code | Claude Agent SDK    | 必须遵守工具权限配置          |
| Cursor      | Cursor CLI          | Windows 可用性和具体能力需验证 |

Codex Python SDK 已提供线程运行及工作区访问选项；Claude Agent SDK 提供工具权限控制和会话接口；Cursor CLI 支持非交互执行及结构化输出。

## 五、AgentSync 需要的数据结构

为了避免 Work 临时拼凑数据库，我建议在架构阶段明确以下实体。

| 数据表                 | 保存内容           | 主要用途          |
| ------------------- | -------------- | ------------- |
| `projects`          | 项目 ID、路径、配置    | 项目隔离          |
| `agents`            | Agent ID、类型、能力 | Agent 身份与能力   |
| `sessions`          | 会话、心跳、状态       | 判断 Agent 是否在线 |
| `tasks`             | 任务、负责人、状态、版本   | 共享任务板         |
| `task_dependencies` | 任务依赖关系         | 调度顺序          |
| `task_leases`       | 认领者、租约、过期时间    | 避免重复认领        |
| `resource_locks`    | 文件、目录、锁状态      | 协作式冲突防护       |
| `context_entries`   | 共享记忆、来源、版本     | 跨 Agent 上下文   |
| `handoffs`          | 交接资料、变更、证据     | 任务交接          |
| `runs`              | 执行 ID、适配器、结果   | 控制适配器管理       |
| `approvals`         | 请求、审批人、决定      | 权限审批          |
| `usage_records`     | Token、费用及来源    | 用量统计          |
| `audit_events`      | 操作类型、时间、主体     | 审计与恢复         |

### 任务状态机

pending — 待认领

claimed — 已认领

running — 执行中

review — 待验收

completed — 已验收完成

另外支持 blocked、failed、cancelled、expired 等分支，并记录合法状态转换。

关键是让 Work 实现真正的状态约束。比如两个 Agent 不能同时拥有同一个排他任务；已过期租约的 Agent 不能继续提交该任务的有效更新。

## 六、MCP 工具清单与 API 设计

为了让不同 AI 客户端真正能够使用 AgentSync，建议第一版就定义稳定的工具名称和参数结构。

| MCP 工具              | 功能           | 阶段    |
| ------------------- | ------------ | ----- |
| `register_agent`    | 注册 Agent 和能力 | M1–M2 |
| `heartbeat`         | 更新会话在线状态     | M1–M2 |
| `create_task`       | 创建任务         | M1–M2 |
| `list_tasks`        | 查询项目任务       | M1–M2 |
| `claim_task`        | 排他认领任务       | M1–M2 |
| `update_task`       | 更新进度与状态      | M1–M2 |
| `get_project_state` | 获取项目全局状态     | M1–M2 |
| `publish_context`   | 保存共享上下文      | M3    |
| `get_context`       | 查询项目记忆       | M3    |
| `submit_handoff`    | 提交交接包        | M3    |
| `acquire_lock`      | 申请文件锁        | M4    |
| `release_lock`      | 释放文件锁        | M4    |
| `submit_for_review` | 提交验收证据       | M5    |
| `get_run_status`    | 查看运行中的任务     | M6    |
| `get_usage_summary` | 查询已知用量       | M8    |

所有工具都应包含明确的 `project_id`，涉及写入的操作还应具备会话权限验证、版本校验及适当的幂等保护。

另外要区分两种 API：

- AgentSync HTTP API：让其他程序控制 AgentSync，包括创建任务、查询状态、提交交接包。
- LLM Provider API：AgentSync 在自主调度模式下，调用用户自己配置的 GPT、Claude 等模型。

前者是我们提供的接口；后者是我们需要兼容的外部服务。

跨客户端最终验收：

使用测试项目，让两个独立的 AI 客户端连接同一 AgentSync 实例。Agent A 认领开发任务，Agent B 查询状态后认领审查任务。双方能够交接结果、检测模拟冲突、查看审计记录。

## 九、风险控制和开发原则

| 主要风险             | 必须采取的措施                         |
| ---------------- | ------------------------------- |
| 第三方 SDK 更新后失效    | 版本固定、能力检测、兼容性测试                 |
| 不同 MCP 客户端行为不同   | 每个客户端单独验证                       |
| 多 Agent 同时修改同一文件 | Git Worktree + 协作式锁 + 冲突检测      |
| Agent 无限重复执行任务   | 步数、时间、调用次数和预算上限                 |
| 任务崩溃后数据混乱        | 持久化事件、租约、幂等操作                   |
| API Key 泄漏       | 凭据隔离、环境变量、日志脱敏                  |
| Agent 执行未授权操作    | 审批机制、受控工作区、最小权限                 |
| 开发过程中产生费用        | 默认 Mock、禁止未经授权的真实付费调用           |
| Work 会话中断        | `PROGRESS.md` + Git 检查点 + 可复现命令 |
| 免费软件被误解成免费模型     | 明确标注 BYOK 费用由用户承担               |

对于 HTTP 服务，默认只允许本地回环地址访问，并加入访问控制；如未来支持远程访问，再专门设计身份认证、加密传输与部署安全。

## 一、最终产品目标

项目名称暂定为 AgentSync。

AgentSync 是一个免费、MIT 开源、模型无关、支持本地部署的跨平台多 AI Agent 协作与调度系统。

支持两种模式：

**模式 A：MCP 协作模式**

让已经运行的 Codex、Claude Code、Cursor 或其他兼容 MCP 的 AI Agent 主动调用 AgentSync，完成任务登记、认领、状态查询、项目记忆共享、协作式文件锁、任务交接及结果验收。

**模式 B：主动调度模式**

AgentSync 可以通过各厂商公开支持的 SDK/CLI，主动创建并管理 Agent 运行会话，将不同任务分配给多个 Agent，读取执行状态、收集结果和错误信息、协调交接。

注意：启动新的 Agent 会话不等于控制已有桌面应用窗口，不得虚构控制能力。

另外必须支持：

- Python SDK
- 本地 HTTP REST API
- 用户自带模型 API Key
- 可选的 GPT、Claude、Gemini、DeepSeek、Ollama 等模型接口
- 完全不依赖付费模型的基础协作模式

不需要开发独立桌面 GUI。

5. Agent 交接失败或信息缺失。
